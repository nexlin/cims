================================================================================
 CIMS TB 설치 순서서 — 깡통 서버 1대에 설치해서 호시험까지
================================================================================

 대상 구성
   · 서버 1대에 전부 (DB + OAM/콘솔 + csp + cmp + csc + oam-svc)
   · HA(이중화) 미사용
   · 서비스 계정 = cims
   · OS = Ubuntu 26.04 LTS 또는 Rocky Linux 10.2 / x86_64  (아래 §1 참고)
        배포판 이름이 조건이 아니라 **능력 셋**이 조건이다 — x86_64 · glibc 2.38 이상 ·
        CPython 3.14. 설치 스크립트가 이름이 아니라 이 셋을 검사한다.

 읽는 법
   $ 로 시작하는 줄이 실제로 칠 명령이고, 그 아래 들여쓴 줄이 그 명령의 설명이다.
   [확인] 은 결과가 이렇게 나와야 한다는 뜻이다.
   [주의] 는 틀리면 나중에 원인 찾기 어려운 항목이다.

 어디서 치는 명령인가
   §0 은 **빌드 장비(인터넷 되는 개발서버)** 에서 치는 명령이다 — 반입본 tar 를 만드는 절이다.
   §1 부터가 **TB 서버(깡통)** 에서 치는 명령이다.
   반입본 tar 를 이미 받아왔다면 §0 은 건너뛰고 §1 부터 시작한다.


================================================================================
 0. 가져갈 것  (TB 가기 전에 빌드 장비 = 개발서버에서 준비)
================================================================================

 결과물은 파일 하나다:  cims-tb-<날짜>.tar.gz   (USB 에 담아 간다)
 그 안에 아래가 전부 들어 있다.

   설치 스크립트          deployment/tb/ 전체 (이 파일 포함)
   DB 부트스트랩          db_bootstrap.py + cims_schema.sql + pymysql
   OS 패키지              debian 계열 = MariaDB .deb / rhel 계열 = MariaDB .rpm
                          (반입본에는 수집해 둔 계열만 들어 있다 — 0-3 참고)
   동봉 인터프리터        CPython 3.14 재배치 빌드 (배포판이 3.14 를 안 줄 때 쓴다 — 0-3b)
   모듈 패키지            cims-bootstrap-*.tar.gz + csp/cmp/csc/oam-svc(+cspsim)
   초기 데이터 CSV        조직·사용자·가입번호·PTT그룹
   시험용 미디어          tests/media (호시험 코덱용)

 --------------------------------------------------------------------------------
 0-1. 어느 클론에서 패키징하는가
 --------------------------------------------------------------------------------

  TB 반입본은 **개발 클론**에서 만든다. 0-2 ~ 0-5 가 전부 이 트리에서 돈다.

  $ cd /home/user01/cims
      TB 스크립트(deployment/tb)가 여기 있고, 상류(main)를 따라간다.

  $ ls -d deployment/tb
      [확인] 있어야 한다. 워크트리에서 작업했다면 이 클론으로 먼저 복사한다:
               cp -a <워크트리>/deployment/tb /home/user01/cims/deployment/
      [주의] deployment/tb 는 git 에 커밋하지 않는다 (로컬 보관).
             두 사본이 갈라지면 워크트리가 원본이다.

      [주의] /home/user01/cims-pkg 는 **쓰지 않는다.** 그 클론은 라이브 관리서버 배포
             출처(브랜치 local-patches)여서 상류보다 뒤처져 있고 버전 번호도 따로
             올라간다 — TB 에 쓰면 옛 코드가 실린다. 지연은 이렇게 본다:
               git -C /home/user01/cims-pkg rev-list --count HEAD..origin/main

 --------------------------------------------------------------------------------
 0-2. 모듈 패키지 만들기
 --------------------------------------------------------------------------------

  $ cd /home/user01/cims
  $ mkdir -p build && cd build && cmake ..
      첫 빌드면 외부 의존(oneTBB·opencore-amr·googletest 등)을 인터넷에서 받는다.
      그래서 이 작업은 반드시 인터넷 되는 곳에서 해야 한다.

  $ make -j$(nproc)
      C++ 바이너리(csp·cmp·cmdp·cspsim)를 build/bin 에 만든다.

  $ make dist
      [주의] 이걸 빼먹으면 안 된다. make 는 build/bin 만 갱신하고,
             패키징은 build/dist 를 담는다. 빼먹으면 옛 바이너리가 조용히 실린다.

  $ cd .. && ./cims.sh pkg
      모듈별 tarball 을 build/dist/packages/ 에 만들고,
      부트스트랩 인스톨러(cims-bootstrap-<oam버전>.tar.gz)도 함께 조립한다.

  $ ls build/dist/packages/
      [확인] cims-bootstrap-*.tar.gz · csp-*.tar.gz · cmp-*.tar.gz ·
             csc-*.tar.gz · oam-svc-*.tar.gz · agent-*.tar.gz · cspsim-*.tar.gz

 --------------------------------------------------------------------------------
 0-3. MariaDB .deb 수집  (폐쇄망엔 apt 저장소가 없다)
 --------------------------------------------------------------------------------

  $ deployment/tb/tools/tb-fetch-debs.sh mariadb
      MariaDB 서버·클라이언트와 그 의존 패키지를 받아
      deployment/tb/offline/debs/mariadb/ 에 담고, apt 색인(Packages)도 만든다.
      [확인] "40개, 32M" 같은 요약이 나온다. 개수는 배포판 상태에 따라 다를 수 있다.

  $ deployment/tb/tools/tb-fetch-debs.sh apt-repair
      **대상 장비의 apt 가 이미 깨져 있을 때** 그것을 메우는 최소 집합
      (libnl-3-200 · libnl-genl-3-200 · libsnmp40t64 + 의존)이다.
      apt 는 설치 요청 전에 시스템 전체 의존을 검사하므로, 관계없는 패키지의 구멍
      하나가 MariaDB 설치까지 거부한다 — 폐쇄망에서는 받아올 곳이 없어 영구히 막힌다.
      keepalived 를 지울 때 libnl 이 함께 걷혀 가는 경우가 대표적이다.
      05 단계는 debs/ 아래 **모든 세트**를 저장소로 붙이므로 함께 해석된다.

  ── rhel 계열(로키·RHEL) 대상이면 ────────────────────────────────────────────
  대상 장비가 로키/RHEL 이면 .deb 가 아니라 .rpm 이 필요하다. **rpm 은 빌드 장비(우분투)
  에서 받을 수 없다** — 같은 배포판·같은 메이저 버전 장비에서 받아야 한다.

  **sudo 로 돌린다.** 받기만 하고 아무것도 설치하지 않지만, 마지막에 "이 묶음만으로 설치가
  풀리는가" 를 dnf 에게 실제로 풀어 보게 하는 검사가 있고 그 해결에 root 가 필요하다.
  (비root 로 돌리면 그 검사만 건너뛴다 — 빠진 의존이 폐쇄망 현장에서야 드러난다.)

  $ ./tools/tb-fetch-rpms.sh mariadb        (로키 장비에서, 반입본을 푼 자리에서)
      MariaDB 서버·클라이언트 + mariadb-connector-c 와 의존을 받아
      offline/rpms/mariadb/ 에 담는다.
      connector 를 함께 받는 이유: csp(C++)가 libmariadb.so.3 를 링크한다. debian 쪽은
      csp 패키지가 이것을 .deb 로 동봉하지만 rpm 동봉물은 아직 없다.
      [확인] Rocky 10.2 실측 — 191개 74M. 목록에 mariadb-server · mariadb ·
             mariadb-connector-c 가 보여야 한다.

  [참고] **CPython 3.14 는 rpm 으로 받지 않는다** — 반입본이 인터프리터를 동봉한다
         (0-3b 참조). 배포판 패키지로 깔아야 하는 사정이 있을 때만 아래를 쓴다:
           ./tools/tb-fetch-rpms.sh python      (offline/rpms/python/, 54개 32M)
         05 단계는 **동봉본을 먼저** 보므로, 둘 다 있으면 rpm 은 쓰이지 않는다.

      [확인] 마지막에 "dnf 가 이 묶음만으로 설치를 풀 수 있습니다" 가 나와야 한다.
             안 나오면 빠진 패키지 이름이 함께 찍히니, 그 이름으로 같은 디렉토리에 더 받는다:
               dnf download --resolve --alldeps --destdir offline/rpms/<set> <패키지명>
             `dnf download --resolve` 가 **조건부(rich) 의존을 따라가지 않기 때문에** 생기는
             일이다 — mariadb-server 의 `(mysql-selinux >= 1.0.10 if selinux-policy-targeted)`
             가 실제로 그렇게 빠졌다. 그래서 이 검사를 둔다.

      [주의] 받은 rpm 은 **그 배포판 전용**이다. Rocky 10 용을 RHEL 9 에 깔 수 없다.

      [주의] 의존을 `--alldeps` 로 받기 때문에 **기반 패키지까지 함께 담긴다**
             (glibc·bash·coreutils·systemd·filesystem 등). 일부러 그렇게 한다 —
             "수집 장비엔 있고 대상 장비엔 없어서" 폐쇄망에서 영구히 막히는 사고를
             막기 위해서다(deb 쪽 lsof/psmisc/rsync 사례).
             설치 때 dnf 가 이미 같은 버전인 것은 건너뛴다. 다만 **대상 장비가 더 낮은
             버전이면 그것들을 올린다** — 수집 장비와 대상 장비를 같은 이미지에서
             만든 것으로 맞추면 아무 일도 일어나지 않는다.

  [참고] 수집에서 제외하는 것은 Priority=required/important 뿐이다. `standard` 는
         "표준 설치에 포함" 이지 "모든 설치에 포함" 이 아니라서(최소·클라우드 이미지에는
         없다) 제외하지 않는다. 정확버전(=)으로 묶인 짝(perl ↔ perl-base 등)은 우선순위와
         무관하게 함께 담는다 — 한쪽만 담으면 대상 장비에서 절대 풀리지 않는다.

 --------------------------------------------------------------------------------
 0-3b. 동봉 인터프리터 (CPython 3.14)
 --------------------------------------------------------------------------------

  OAM·CSC 안의 부품 13개가 CPython 3.14 전용으로 컴파일돼 있다. 그런데 배포판이 3.14 를
  주지 않는 경우가 있다 — Rocky 10.0·10.1 저장소에는 python3.14 패키지가 아예 없다
  (10.2 부터 생겼다). 그래서 인터프리터를 **반입본에 동봉한다.**

  $ deployment/tb/tools/tb-fetch-python.sh      (인터넷 되는 빌드 장비에서)
      재배치 가능 빌드(python-build-standalone)를 받아 offline/runtime/ 에 담는다.
      버전·sha256 이 스크립트에 고정돼 있고, 이미 받아 뒀으면 건너뛴다.
      [확인] "python-3.14.7.tar.gz (35M)" · "sha256 일치"

      [참고] 이 빌드는 **glibc 외에 아무것도 요구하지 않는다** (OpenSSL·SQLite 내장).
             그래서 배포판·마이너가 바뀌어도 그대로 동작한다 — 버전에 묶이는 쪽은
             오히려 배포판 rpm 이다. 대상 장비의 05 단계가 이것을
             <설치경로>/runtime/python 에 풀고, agent·OAM·CSC 가 그 인터프리터로 뜬다.

 --------------------------------------------------------------------------------
 0-4. 호시험용 미디어 — tb-pack.sh 가 자동으로 담는다
 --------------------------------------------------------------------------------

      0-5 의 tb-pack.sh [5/5] 단계가 tests/media 의 파일을 offline/media 로 복사한다
      (약 7.4MB). 손으로 넣을 필요가 없다.

      [알아둘 것] **파일명은 상관없다.** cspsim 은 그 디렉토리에서 `*_audio.amrwb` 를
             모아 이름과 무관하게 단말 순번대로 돌려 쓴다 (i번째 단말 → i % 파일수).
             그래서 필요한 것은 파일이 "있는지" 뿐이고, 초기 데이터 CSV 의 번호를
             바꿔도(§3 재번호) 미디어는 손댈 필요가 없다.
             파일명이 번호처럼 생긴 것은 자료를 만들 때의 관례일 뿐이다.

      [주의] 파일이 하나도 없으면 전 세션이 합성음 PCMU(codec(0))로 떨어진다 —
             호는 서지만 녹취 재생이 안 된다.

      레포 밖에서 따로 넣어야 하면:
        $ mkdir -p deployment/tb/offline/media
        $ cp -a tests/media/. deployment/tb/offline/media/

 --------------------------------------------------------------------------------
 0-5. 반입본 한 덩어리로 묶기
 --------------------------------------------------------------------------------

  $ deployment/tb/tools/tb-pack.sh --with-packages --tar
      db_bootstrap.py·스키마·pymysql 을 offline/db-bootstrap/ 으로 모으고,
      build/dist/packages/*.tar.gz 를 offline/packages/ 로 복사한 뒤,
      deployment/tb 전체를 build/dist/cims-tb-<날짜>.tar.gz 로 묶는다.
      사이트 값(tb-site.conf)·임시 자격(state/)·로그(log/)는 제외된다.
      단말 대면 인증서 도구(scripts/service-cert.sh)도 offline/tools/ 로 함께 담는다
      (4-8 에서 쓴다).

      [주의] 파일명에 **날짜만** 들어간다 — 같은 날 다시 묶으면 앞의 것을 덮어쓴다.
             남겨야 할 판이 있으면 먼저 이름을 바꿔 두고, 대상 장비에 옮긴 뒤에는
             .sha256 으로 어느 판인지 확인한다.

  $ ls -lh build/dist/cims-tb-*.tar.gz*
      [확인] tar.gz 와 같은 이름의 .sha256 두 개가 나온다.
             tb-pack.sh 가 sha256 을 찍고 옆에 파일로도 남긴다.

  $ cp build/dist/cims-tb-*.tar.gz build/dist/cims-tb-*.tar.gz.sha256 /media/<USB경로>/
      USB 로 복사. **.sha256 을 같이 가져간다** — 대상 장비에서 대조용이다.
      FTP·scp 로 보낼 거면 §2-b 를 본다.


================================================================================
 1. TB 서버 전제 확인  (설치 시작 전 5분)
================================================================================

 일반 계정으로 로그인한다 (root 직접 로그인은 스크립트가 거부한다).

  $ cat /etc/os-release | head -3
      배포판 이름 자체는 조건이 아니다. 조건은 아래 셋이고, 05 단계가 이것을 검사한다.
      실측 통과: Ubuntu 26.04 LTS · Rocky Linux 10.2.

  $ uname -m
      [확인] x86_64   — 동봉 바이너리(csp·cmp·cspsim) 아키텍처다.

  $ ldd --version | head -1
      [확인] 끝의 숫자가 2.38 이상이어야 한다 (우분투 26.04 = 2.43, 로키 10.2 = 2.39).
      [주의] 낮으면 csp 가 실행 즉시 죽는다 — 설정으로 풀 수 없고 재빌드가 필요하다.
             csp 가 링크한 최고 심볼이 GLIBC_2.38 이다.

  $ python3 -V; python3.14 -V 2>/dev/null
      [확인] 둘 중 하나가 Python 3.14.x 여야 한다.
             우분투 26.04 — 기본 python3 이 3.14 다.
             로키 10.2   — 기본은 3.12 이고, 3.14 는 별도 패키지다:
                             sudo dnf install -y python3.14
                           (반입본에 담아 왔다면 05 단계가 알아서 깐다)
      [주의] 3.14 가 없으면 20 단계에서 OAM 이 기동 자체를 못 한다. OAM·CSC 안에 든
             부품 13개가 `*.cpython-314-*.so` — CPython 3.14 전용 바이너리라서다.
             설치 스크립트는 이름이 아니라 **버전을 물어서** 인터프리터를 고르므로,
             자리가 /usr/bin/python3 든 /usr/bin/python3.14 든 상관없다.

  $ ip -4 -o addr show scope global | awk '{print $2, $4}'
      이 서버의 IP 를 확인해 적어둔다. 아래에서 계속 쓴다.
      1대 구성이면 관리 IP = SIP IP = RTP IP 로 같은 주소를 쓴다.

  $ sudo -v
      sudo 가 되는지 확인 (비밀번호 물어보면 정상).

  $ id cims 2>/dev/null || echo "cims 계정 없음"
      서비스 계정 확인. 없으면 만든다:

  $ sudo useradd -m -s /bin/bash cims
      [주의] -m(home) 과 -s /bin/bash(로그인 셸)가 반드시 필요하다.
             부트스트랩이 `su - cims` 로 전환하기 때문이다.

  $ df -h /opt /var
      디스크 여유 확인. 모듈·로그(/opt)와 DB(/var)가 들어간다.
      [주의] MariaDB datadir 은 배포판마다 다르다 — 우분투 26.04 는 /var/lib/mariadb
             (26.04 에서 기본값이 바뀌었다), 로키 10 은 /var/lib/mysql 이다.
             스크립트는 둘 다 본다.


================================================================================
 1-R. 로키(rhel 계열)에서 추가로 해야 하는 것  ★ 우분투면 이 절을 건너뛴다
================================================================================

 우분투와 다른 점만 모았다. **설치 흐름(§2~§5)은 같고**, 아래 넷이 더 붙는다.
 대부분 스크립트가 알아서 하지만, 무엇이 왜 다른지 알고 있어야 막혔을 때 빨리 푼다.

 R-1. CPython 3.14 — 배포판이 안 줄 수 있다
 --------------------------------------------------------------------------------
   OAM·CSC 안의 부품 13개가 3.14 전용으로 컴파일돼 있다. 로키의 기본 python3 은 3.12 다.
     · Rocky 10.2  — AppStream 에 python3.14 가 있다
     · Rocky 10.0 / 10.1 — **없다** (python3.<버전> 패키지 자체가 10.2 부터 생겼다)
   그래서 반입본이 인터프리터를 동봉한다(§0-3b). 05 단계가 그것을
   <설치경로>/runtime/python 에 풀고, agent·OAM·CSC 가 그 인터프리터로 뜬다.
   [확인] 05 에서 "python 3.14: ..." 줄이 나온다.

 R-2. OS 패키지는 .rpm 이고, 같은 배포판 장비에서 받아야 한다
 --------------------------------------------------------------------------------
   빌드 장비(우분투)에서는 rpm 을 받을 수 없다. 대상과 **같은 배포판·같은 마이너**
   장비에서 §0-3 의 tb-fetch-rpms.sh 로 받아 offline/rpms/ 에 담는다.
   [주의] `dnf download --resolve` 는 **조건부(rich) 의존을 따라가지 않는다.**
          mariadb-server 의 `(mysql-selinux >= 1.0.10 if selinux-policy-targeted)` 가
          그래서 빠진 적이 있다. 수집기가 마지막에 "dnf 가 이 묶음만으로 설치를 풀 수
          있습니다" 를 확인하므로, 그 줄을 반드시 보고 넘어간다.
   [주의] 받은 rpm 에는 glibc·systemd 같은 기반 패키지도 함께 담긴다(일부러 그렇다).
          대상 장비의 마이너가 더 낮으면 설치하면서 그것들이 올라간다 — 수집 장비와
          대상 장비를 같은 이미지로 맞추면 아무 일도 없다.

 R-3. 시스템 DB 는 설치가 아니라 첫 기동 때 만들어진다
 --------------------------------------------------------------------------------
   우분투는 패키지 설치 시점(postinst)에 mariadb-install-db 를 돌리지만, rhel 은
   mariadb.service 의 ExecStartPre(mariadb-prepare-db-dir)가 **첫 기동 때** 만든다.
   그래서 05 직후에 /var/lib/mysql/mysql 이 없는 것이 **정상**이다 — 05 는 그 사실을
   알리고 넘어가고, 10 단계가 기동하면서 만든다.
   [참고] datadir 도 다르다 — 우분투 /var/lib/mariadb · 로키 /var/lib/mysql.

 R-4. firewalld — 포트를 열어야 한다  ★ 가장 자주 걸리는 것
 --------------------------------------------------------------------------------
   로키는 firewalld 가 **기본 켜짐**이고 ssh 말고는 전부 거부한다. 우분투는 ufw 가 기본
   꺼짐이라 이 관문 자체가 없었다. 증상이 고약하다 — 서버에서는 `curl` 이 200 인데
   **브라우저만 안 붙는다.** 바깥에서 보면 `No route to host` 가 돌아온다(거부 응답).

   20 단계가 OAM/콘솔 포트를 자동으로 연다. **단말이 붙는 포트는 tools/tb-firewall.sh
   가 연다** — 모듈 설치(40 단계) 뒤에 돌린다.

   $ sudo ./tools/tb-firewall.sh --dry-run
       무엇을 왜 열지 계획만 보여준다. 포트 숫자를 이 스크립트가 들고 있지 않다 —
       SIP 는 tb-site.conf/pkg_setting.cfg 에서, 미디어 대역은 **배포된 cmp.json 의
       시작포트 + 풀 크기로 계산**한다. 그래서 설정을 바꾸면 다시 돌리기만 하면 된다.

   $ sudo ./tools/tb-firewall.sh
       계획을 보여주고 물어본 뒤 연다 (--yes 로 묻지 않게).

       [확인] 템플릿 기본값 그대로면 이렇게 나온다:
         4419/tcp         콘솔·API
         4430/tcp         CSC 단말 대면 HTTPS (4-8 인증서와 짝)
         5060/udp · 25061/tcp · 5061/tcp    SIP
         50000-50159/udp  VoLTE/VoIP 미디어 (RtpStartPort + RtpPoolSize × 8)
         52000-52079/udp  PTT 멤버 오디오   (PttRtpStartPort + PttMemberPoolSize × 2)
         56000-56079/udp  PTT 멤버 영상
         54000-54019/udp  PTT floor 제어    (PttFloorStartPort + PttRtpPoolSize × 2)
         58000-58063/udp  감청 tap          (TapStartPort + TapPoolSize × 4)

       [주의] 내부 채널은 열지 않는다 — csc 내부 API(4421) · csp 제어(9000) ·
              cmp 제어(9001) · DB(3306). 목록에 없는데 외부 주소로 듣고 있는 포트가
              있으면 **알려만 준다**(자동으로 열지 않는다) — 여는 목록이 곧 노출면이다.

   $ sudo firewall-cmd --list-ports
       [확인] 템플릿 기본값이면 **11개**가 보인다 (Rocky 10.2 실측):
         4419/tcp 4430/tcp 5061/tcp 10022/tcp 25061/tcp 5060/udp
         50000-50159/udp 52000-52079/udp 54000-54019/udp 56000-56079/udp 58000-58063/udp

   ★ **바깥 장비에서 반드시 한 번 확인한다.** 서버에서 `--list-ports` 가 맞아도 상위
     네트워크에서 막히면 증상이 똑같다. 다른 장비에서:

   $ for p in 4419 4430 5061 25061; do printf '%s ' $p; \
       timeout 5 bash -c "cat </dev/null >/dev/tcp/<서버IP>/$p" 2>/dev/null \
       && echo 열림 || echo 차단; done
       [확인] 넷 다 `열림`. 그리고 **내부 포트는 막혀 있어야 한다**(음성 대조군):
              9000(csp 제어) · 3306(DB) · 16000(csp Monitor API) → `차단`
              열려 있으면 방화벽 규칙이 과하게 들어간 것이다.

   [참고] 자동 개방이 싫으면 TB_SKIP_FIREWALL=1 로 끄면 안내만 나온다.
   [참고] 포트를 열어도 단말은 아직 못 붙는다 — 4-8 의 인증서가 남아 있다.
          **포트 막힘과 인증서 불일치는 증상이 똑같다**(로그인 실패 + CSC 로그에 요청
          없음). 그래서 방화벽을 먼저 끝내고 확인한 뒤 4-8 로 넘어간다.

 R-5. SELinux — 막은 것이 없다 (전 구간 실측)
 --------------------------------------------------------------------------------
   enforcing 상태 그대로 **05~70 전 구간(설치·설정·기동·호시험)이 통과했고 AVC 거부
   기록이 0건**이다 (Rocky 10.2, 2026-09-11). 끄거나 완화할 이유가 없다.

   $ sudo ausearch -m AVC -ts today
       [확인] 아무것도 안 나오면 정상이다.

   모듈이 표준 자리가 아닌 경로(/opt/cims-agent)에서 돌고 파일 capability(CAP_NET_ADMIN)
   도 쓰므로, 앞으로 막히는 일이 생기면 여기를 먼저 본다. 끄는 것은 마지막 수단이다 —
   무엇이 막혔는지부터 본다.

 R-6. 모듈 로그는 한 단계 더 깊은 자리에 있다
 --------------------------------------------------------------------------------
   `<설치경로>/modules/<모듈>/current/log/<모듈>.log` 는 **agent 가 받은 stdout** 이라
   비어 있을 수 있다(CSP 는 0바이트다). 모듈이 제 로그를 쓰는 자리는 한 단계 더 깊다:

     /opt/cims-agent/modules/csp/current/csp/log/csp_<날짜>_N.log     ← 실제 SIP 로그
     /opt/cims-agent/modules/oam/current/oam/log/app_<날짜>.log
     /opt/cims-agent/modules/csc/current/csc/log/app_<날짜>.log

   $ sudo find /opt/cims-agent/modules -name '*.log' -size +0 -printf '%10s  %p\n' | sort -rn | head
       어느 로그에 내용이 있는지 한 번에 본다. (rhel 전용 항목은 아니지만 로키에서
       처음 걸렸다 — 빈 파일을 보고 "로그가 안 남는다" 로 오해하기 쉽다.)


================================================================================
 2. 반입본 풀기
================================================================================

 반입본이 이 서버에 들어온 경로에 따라 2-a(USB) 또는 2-b(FTP/SCP) 를 쓴다.
 2-c 부터는 공통이다. 이미 이 서버에 파일이 있으면 2-a·2-b 를 건너뛰고 2-c 로 간다.

 --------------------------------------------------------------------------------
 2-a. USB 로 가져온 경우
 --------------------------------------------------------------------------------

  $ lsblk -o NAME,SIZE,LABEL,MOUNTPOINT
      USB 가 어디에 붙었는지 본다. 자동 마운트가 안 됐으면 직접 붙인다:
        sudo mkdir -p /media/usb && sudo mount /dev/sdb1 /media/usb

  $ cd /media/<USB경로> && sha256sum -c cims-tb-<날짜>.tar.gz.sha256
      [확인] "cims-tb-<날짜>.tar.gz: OK"
             .sha256 을 안 가져왔으면 빌드 장비에서 적어둔 값과 `sha256sum` 결과를
             눈으로 대조한다.
      [주의] `-c` 에 주는 것은 **.sha256 목록 파일**이다 (tar.gz 본체가 아니다).
             본체를 주면 Ubuntu 26.04 의 sha256sum(uutils 판)이 거부가 아니라
             panic 으로 죽는다: "index out of bounds ... validate.rs".
             목록 안의 파일명이 경로 없는 이름이라, **tar.gz 이 있는 디렉토리에서**
             실행해야 한다.

  $ mkdir -p ~/cims-tb && cd ~/cims-tb
  $ tar xzf /media/<USB경로>/cims-tb-<날짜>.tar.gz
      [확인] tb/ 디렉토리가 생긴다.

 --------------------------------------------------------------------------------
 2-b. FTP / SCP 로 올린 경우
 --------------------------------------------------------------------------------

  [주의] FTP 는 **반드시 binary 모드**로 올린다. ascii 모드로 올리면 tar.gz 가
         조용히 깨진다(개행 변환). 아래 sha256 확인이 그걸 잡는 유일한 장치다.
         SSH 가 열려 있으면 FTP 대신 scp 를 쓰는 게 안전하다 — 모드 개념이 없다.

  (1) 올리는 쪽 = 빌드 장비

  $ cat build/dist/cims-tb-<날짜>.tar.gz.sha256
      tb-pack.sh 가 남긴 값. 이 파일을 tar.gz 와 **함께** 보낸다.

  $ scp build/dist/cims-tb-<날짜>.tar.gz{,.sha256} <계정>@<TB서버>:~/
      scp 를 쓸 수 있으면 이게 가장 단순하다 (둘 다 한 번에).

  $ lftp -u <계정> <TB서버> -e "set ftp:passive-mode on; binary; \
         put build/dist/cims-tb-<날짜>.tar.gz -o cims-tb-<날짜>.tar.gz; bye"
      FTP 를 써야 할 때. binary 를 명령에 박아 넣어 실수를 막는다.

  $ ftp <TB서버>
      대화식 ftp 라면 put 전에 binary 를 먼저 친다:
        ftp> binary
        ftp> put cims-tb-<날짜>.tar.gz
        ftp> bye
      [주의] `binary` 를 빼먹으면 전송은 성공한 것처럼 끝나고 압축 해제에서
             "gzip: unexpected end of file" 로 터진다.

  (2) 받는 쪽 = TB 서버

  $ ls -l ~/cims-tb-<날짜>.tar.gz
      [확인] 바이트 수가 올린 쪽과 정확히 같아야 한다.

  $ cd ~ && sha256sum -c cims-tb-<날짜>.tar.gz.sha256
      [확인] "cims-tb-<날짜>.tar.gz: OK"
             .sha256 도 같이 올렸으면 이 한 줄로 끝난다.
             (.sha256 은 텍스트라 ascii 모드로 올려도 깨지지 않는다)
      [주의] FAILED 면 전송이 깨진 것이다 — 풀지 말고 binary 모드로 다시 올린다.
             ascii 모드 사고가 여기서 잡힌다.
      [주의] `-c` 에 주는 것은 **.sha256 목록 파일**이다 (tar.gz 본체가 아니다).
             본체를 주면 Ubuntu 26.04 의 sha256sum(uutils 판)이 거부가 아니라
             panic 으로 죽는다: "index out of bounds ... validate.rs".
             목록 안의 파일명이 경로 없는 이름이라, **tar.gz 이 있는 디렉토리에서**
             실행해야 한다.

  $ ls -l ~/cims-tb-<날짜>.tar.gz
      [주의] FTP 계정과 설치 계정이 다르면 소유자가 어긋난다. 다르면 정정한다:
               sudo chown $(id -un):$(id -gn) ~/cims-tb-<날짜>.tar.gz

  $ mkdir -p ~/cims-tb && cd ~/cims-tb
  $ tar xzf ~/cims-tb-<날짜>.tar.gz
      [확인] tb/ 디렉토리가 생긴다.

 --------------------------------------------------------------------------------
 2-c. 공통 — 풀린 내용 확인
 --------------------------------------------------------------------------------

  $ cd ~/cims-tb/tb && ls
      [확인] tb-install.sh · steps/ · lib/ · data/ · offline/ · tools/ · README.md

  $ ls -l tb-install.sh
      [확인] 실행 권한(x)이 있어야 한다. 없으면: chmod +x tb-install.sh tools/*.sh
             (tar 는 권한을 보존하지만, 중간에 재압축을 거치면 잃을 수 있다)

  $ ls offline/packages/ offline/debs/mariadb/ | head -20
      [확인] 모듈 tarball 과 .deb 이 들어 있다.

  $ ./tb-install.sh --help
      역할 목록과 옵션을 확인한다. 여기서는 아직 아무것도 바꾸지 않는다.

 [주의] 이후 모든 명령을 sudo 로 실행한다. 중간에 sudo 없이 돌리면
        사이트 설정 파일(tb-site.conf, 0600 root 소유)을 읽지 못해 값을 다시 묻는다.


================================================================================
 3. 초기 데이터 CSV 준비  (설치 전에 미리 채워두면 편하다)
================================================================================

 data/ 의 CSV 5장이 조직·사용자·가입번호·PTT그룹이 된다. 템플릿에 시험용 4명이
 이미 들어 있으니, TB 에서 그대로 쓸 거면 손대지 않아도 된다.

  $ cat data/subscriptions.csv
      번호·사람·종류(ptt/volte)·imsi·접속서비스·비밀번호가 한 줄에 하나씩 있다.

  $ vi data/users.csv           # 사람 (login_id / 비밀번호 = 단말 로그인 자격)
  $ vi data/subscriptions.csv   # 가입 번호
  $ vi data/ptt_groups.csv      # PTT 그룹
  $ vi data/ptt_group_members.csv
      필요하면 고친다. 빈 칸은 "기본값 사용" 이라는 뜻이다.

  $ ./tools/tb-renumber-csv.py            # 미리보기 (아무것도 바꾸지 않는다)
  $ ./tools/tb-renumber-csv.py --apply    # 반영 (원본은 *.bak)
      번호 체계를 E.164 형태로 일괄 재부여한다 — VoLTE +8213+8자리 / PTT +825+8자리,
      IMSI 는 45033 + 번호숫자. 사람(login_id)의 끝 숫자를 순번으로 써서 같은 사람의
      PTT/VoLTE 가 같은 순번을 갖는다. ptt_group_members.csv 의 번호도 함께 바꾼다.
      **18 단계보다 먼저** 돌린다 — 18 은 번호를 열쇠로 넣으므로, 이미 넣은 뒤에 바꾸면
      옛 행이 남고 새 행이 추가된다. 늦었으면 표를 비우고 18 만 다시 돌린다:
        sudo mariadb -e "DELETE FROM cims.ptt_group_members;
                         DELETE FROM cims.ptt_subscriptions;
                         DELETE FROM cims.volte_subscriptions;"
        sudo ./tb-install.sh --role db-data

 [알아둘 것] 번호를 바꿔도 **미디어 파일은 손대지 않는다** — cspsim 이 파일명과
        무관하게 순번대로 돌려 쓴다 (§0-4).
 [주의] subscriptions.csv 의 service_ref(mcptt/volte)는 §4-5 에서 만드는
        접속서비스 이름과 반드시 같아야 한다. 다르면 단말 등록이 401 로 실패한다.


================================================================================
 4. 설치
================================================================================
 단계마다 스크립트가 따로 있다. 순서대로 하나씩 돌린다.
 각 단계는 여러 번 돌려도 안전하고, 실패하면 그 단계만 다시 돌리면 된다.

 처음 돌리는 단계는 필요한 값을 물어본다. 한 번 답한 값은 tb-site.conf 에 저장되어
 다음 단계부터는 다시 묻지 않는다.

 --------------------------------------------------------------------------------
 4-1. DB  (설치 → 설정 → 스키마 → 초기데이터)
 --------------------------------------------------------------------------------

  $ sudo ./tb-install.sh --role db
      05·10·15·18 네 단계를 연속 실행한다.

      [05] 전제 확인(아키텍처·glibc·필수 명령) → 반입 패키지로 MariaDB 설치
             debian 계열 — offline/debs/ 를 로컬 apt 저장소로 붙여 설치
             rhel   계열 — offline/rpms/mariadb/ 를 dnf 로 설치 (+ connector)
                           CPython 3.14 가 없으면 offline/rpms/python/ 으로 함께 설치
             [주의] 반입 패키지가 없으면 여기서 멈춘다. 이 장비에 저장소가 살아 있고
                    네트워크 설치를 허용하려면(= 폐쇄망 동작이 아니다):

      [10] MariaDB 기동·자동기동 + 접속주소 설정 + 임시 관리계정 발급
      [15] DB·앱계정·스키마 생성 → 앱계정 접속 검증 → 임시계정 회수
      [18] data/*.csv → DB 직접 입력

      물어보는 값:
        DB 포트                    → 3306 (엔터)

 --------------------------------------------------------------------------------
 4-5. 패키지 설정   ★ 가장 중요한 단계
 --------------------------------------------------------------------------------

  $ sudo ./tb-install.sh --role config
      두 가지를 넣는다.
        ① 모듈별 설정값(overlay) → 각 모듈 설정 파일에 반영(update_config)
        ② CSP 접속점·접속서비스 컬렉션 → 노드의 jsonl 파일

      ── 넣을 값은 pkg_setting.cfg 에 적혀 있다 ──
      **스크립트에는 값이 없다.** overlay 47키와 컬렉션 5행이 그 파일에 실제 값으로
      들어 있고, 스크립트는 읽어서 OAM 에 넣는 일만 한다. 바꾸려면 그 파일만 고친다.

        $ vi pkg_setting.cfg
        $ sudo ./tb-install.sh --role config      # 고친 값으로 다시 넣기

      파일 맨 위 [vars] 절에 사이트마다 바뀌는 값이 모여 있다 — 보통 여기만 고치면 된다:

        SIP_IP / RTP_IP / MGMT_IP        주소 3개
        SIP_UDP / SIP_TCP / SIP_TLS      리스너 포트 (0 = 미사용)
        PTT_SERVICE / PTT_DOMAIN         PTT 접속서비스 이름·도메인
        VOLTE_SERVICE / VOLTE_DOMAIN     VoLTE 쪽 같은 값
        DB_HOST / DB_PORT / DB_NAME / DB_USER
        CMP_PORT                         CMP 제어·미디어 포트 (cmp ServerPort 와 같아야 한다)

      줄 형식 (자세한 규칙은 파일 머리말):
        <모듈> <키>=<값>              배포 overlay
        <모듈>/<컬렉션> <JSON 객체>   컬렉션 레코드 — 한 줄이 한 행
        [vars]                        위 표의 값들
        ${이름}                       [vars] 또는 tb-site.conf 의 TB_*

      파일에 값을 적지 않고 참조로 남긴 것이 넷뿐이다:
        ${TB_DB_APP_PASS}  DB 비밀번호 — 이 파일은 반입본 tar 에 실려 나가므로 적지
                           않는다. tb-site.conf(0600) 에 두고 45 단계가 물어본다.
        ${STORE} ${SVCLOG} ${CSP_CERT}
                           설치 경로에서 기계적으로 유도되는 경로 셋. 리터럴로 박으면
                           설치 경로를 바꿀 때 조용히 어긋난다.

      [주의] ${이름} 이 없거나 비면 **그 줄 번호를 짚어 중단한다.** 조용히 빈 값이
             들어가면 등록은 되고 동작만 틀려서 원인 찾기가 훨씬 비싸다.
      [주의] 모듈 config_template.json 에 선언이 없는 키는 저장되지 않는다 —
             새 키를 넣으려면 템플릿부터 고쳐야 한다 (아래 [확인] 참고).
      [주의] JwtSecret 은 적지 않는다. OAM 이 그룹 공통 신원으로 주입하므로 손으로
             넣으면 그 신원과 어긋나 토큰 검증이 전부 깨진다.
      [주의] 도메인을 바꾸면 **18 단계도 다시 돌린다** — ha1 이 도메인으로 결박돼
             있어 어긋나면 등록이 401 로만 실패한다. 45 단계가 tb-site.conf 의
             도메인과 대조해 경고해 주지만, 고치는 것은 사람이 해야 한다:
               sudo ./tb-install.sh --role db-data --reconfigure

      ── 물어보는 값 (넷뿐이다) ──
        OAM 주소           → https://127.0.0.1:4419 (엔터)
        콘솔 admin 비번    → §4-3 에서 정한 값 (저장돼 있어 안 묻는다)
        설치 경로          → /opt/cims-agent (엔터)
        DB 비밀번호        → §4-1 값 (저장돼 있어 안 묻는다)

      [확인] 시작할 때 무엇을 넣을지 요약이 먼저 나온다:
               csp/local_nodes 3행 · csp/access_services 2행
               csp 10키 · cmp 5키 · csc 25키 · oam-svc 7키   합계 47키
             이어서 컬렉션 저장과 모듈 4개의 설정 반영(update_config) 완료가 나온다.
      [확인] "미저장(템플릿에 없는 키)" 이 보이면 그 키는 버려진 것이다 — 알려줄 것.

      이 단계가 매뉴얼에 적힌 함정 4개를 값으로 고정한다:
        · csc 자동프로비저닝 포트가 기본값 15060 이면 단말이 못 붙는다 → 5060 으로
        · csc CimsRuntimeDir 이 비면 컬렉션·토큰 경로가 어긋난다 → 관리 store 로
        · local_nodes 에 primary 가 없으면 CSP 가 기동을 중단한다 → UDP 행에 지정
        · TLS 행에 인증서 경로가 없으면 리스너가 안 열린다 → 동봉 csp.pem 으로
        · csc 프로비저닝의 접속서비스 이름(Provisioning.Services.ptt.name) 기본값이
          `ptt` 라 우리 이름 `mcptt` 와 다르다 → 컬렉션과 같은 값으로 묶어 넣는다

 4-6. 콘솔 승격

 4-7. 기동
 --------------------------------------------------------------------------------

  $ sudo ./tb-install.sh --role start
      oam-svc → cmp → csc → csp 순서로 기동한다. 순서에 이유가 있다:
        oam-svc 가 알람 수집기라 먼저 떠야 초기 알람이 유실되지 않고,
        CMP 는 CSP 가 미디어 제어를 붙일 대상이라 CSP 보다 먼저다.

      물어보는 값:
        기동 순서 → "oam-svc cmp csc csp" (엔터)

      [확인] 마지막 표에서 모든 모듈이 status=running / live=up 이어야 한다.
             하나라도 아니면 스크립트가 실패로 알려준다.

  $ ss -lntup | grep -E ':(4419|4421|4430|5060|5061|25061|9000|9001|9010)\b'
      [확인] 콘솔(4419)·csc(4421)·oam-svc(4430)·SIP UDP(5060)·TLS(5061)·TCP(25061)·
             CMP(9000/9001)·FM ingest(9010) 포트가 열려 있다.


 --------------------------------------------------------------------------------
 4-8. 단말 대면 TLS 인증서   ★ 실제 단말을 붙일 때만. 없으면 단말이 로그인하지 못한다
 --------------------------------------------------------------------------------

      cspsim 호시험(§5)만 할 거면 건너뛴다. **사내 단말(Android 앱·Windows
      관제조작반)을 붙일 거면 반드시 한다.**

      왜: 단말은 `CIMS Service CA` 한 장만 신뢰한다. 설치 직후 인증서는 둘 다
      발급자가 다르다 — CSC 4430 은 agent 가 그룹 CA(CIMS-OAM-CA)로 자동 발급한
      것, CSP TLS 는 패키지 동봉 자가서명(cert/csp.pem)이다. 이 상태로 단말이
      붙으면 **로그인 단계에서 TLS 가 끊기고 CSC 로그에는 요청이 한 건도 남지
      않는다.** SIP 를 UDP 로 바꿔도 풀리지 않는다 — 막히는 것은 HTTPS 4430 이다.

      CA 개인키는 CA 보관 서버를 떠나지 않는다. 그래서 두 장소로 나뉜다.

  (1) TB 서버에서 — 이 노드가 요구하는 SAN 을 뽑는다 (설치 전에도 된다)

  $ bash offline/tools/service-cert.sh collect
      [확인] HOST= 와 SAN= 이 출력된다. 이 두 줄을 CA 담당자에게 넘긴다.
             SAN 에는 hostname·127.0.0.1·이 장비의 IPv4 전부·AgentOamUrl 호스트가
             들어간다. 여기 없는 주소로 단말이 접속하면 신원 검증에서 실패한다.

      [주의] **다른 노드용으로 만든 묶음을 IP 가 같다고 재사용할 수 없다.** SAN 에
             hostname 이 들어가므로 호스트명이 다르면 `install` 이 거절한다(exit 2).
             실측(2026-09-11): 같은 IP 121.161.164.49 인데
               기존 묶음 SAN   DNS:media02, IP:127.0.0.1, IP:121.161.164.49, IP:10.0.2.49
               이 노드가 요구  DNS:cims-rocky10.2, IP:127.0.0.1, IP:121.161.164.49
             `DNS:cims-rocky10.2` 가 없어서 재발급이 필요했다. OS 를 다시 깔거나
             호스트명을 바꾸면 인증서도 다시 받아야 한다.

      [주의] 호스트명에 점(.)을 넣으면 그 뒤가 도메인으로 취급된다 — `cims-rocky10.2`
             는 짧은 이름이 `cims-rocky10` 이고 SAN 에는 **긴 이름만** 들어간다.
             단말이 짧은 이름으로 접속하면 실패한다. IP 로 접속하면 무관하다.

  (2) CA 보관 서버에서 — 발급해 묶음을 만든다 (인터넷 불필요, openssl 만)

  $ scripts/service-cert.sh issue --host <HOST> --san "<SAN>"
      → service-cert-<HOST>.tgz 가 나온다. **키가 들어 있다(600) — USB·scp 로만
        옮긴다.** 묶음 안에 같은 스크립트가 복사돼 들어가므로 현장에서는 묶음만
        있으면 된다.

  (3) TB 서버에서 — CSC 가 뜬 뒤(4-7 완료 후) 서비스 계정으로 배치

  $ tar xzf service-cert-<HOST>.tgz
  $ bash service-cert-<HOST>/service-cert.sh install
      [확인] "SAN 대조 통과" → 이 노드가 요구하는 SAN 을 다 담았다는 뜻이다.
             부족하면 배치하지 않고 거절한다 (그대로 두면 agent 가 재기동 때
             그룹 CA 인증서로 덮어써서 단말이 다시 못 붙는다). 그때는 출력된
             issue --force 명령을 CA 서버에서 돌려 다시 받는다.
             "CSC 가 새 인증서를 서빙한다" → 핫리로드 완료. 재시작 불필요.
             기존 파일은 server.crt.bak.<시각> 로 백업된다.

  (4) 콘솔에서 — CSP 가 그 인증서를 쓰게 한다

      [패키지 설정] > csp > local_nodes > TLS 행 (4-5 에서 만든 access-tls)
        tls_cert_path = /opt/cims-agent/modules/csp/runtime/cert/csp-chain.pem
        tls_key_path  = /opt/cims-agent/modules/csp/runtime/cert/csp.key
      저장하면 SIGUSR1 로 무중단 반영된다. 재기동하지 않아도 된다.

  (5) 검증 — 단말을 붙이기 전에 서버측만으로 확정한다

  $ bash service-cert-<HOST>/service-cert.sh verify --ip <단말 접속 IP> \
        --csc-port 4430 --csp-port <TLS bind_port>
      [확인] 전부 PASS. "틀린 이름 거절" 항목은 서버가 신원 검사를 실제로
             집행하는지 보는 음성 대조군이라 PASS 가 정상이다.
      CSC 를 한 번 재시작한 뒤 다시 돌려 발급자가 유지되는지도 본다 — 유지되지
             않으면 SAN 이 부족해 agent 가 덮은 것이다.

      단말 쪽: 로그인 서버 주소는 **SAN 에 있는 IP** 로 넣는다. Windows 관제조작반은
      "서버 인증서 검증"을 켜고 CA PEM 경로에 묶음의 cims-service-ca.crt 를 준다.
      단말 시계가 틀리면 유효기간 검사에서 실패한다.

      절차 정본: docs/user-manual/initial_install.md §4.5 ·
                 docs/design/features/sip_tls_signaling.md §8.3

 5. 호시험  (PTT 그룹호 / VoLTE 호)

  $ sudo ./tb-install.sh --role callcheck
      cspsim(단말 시뮬레이터)으로 등록 → 호 → (PTT 는 floor 까지) 돌려보고 판정한다.
      같은 바이너리에 -mode 만 달리 주고, -db 로 넘긴 가입자 목록에서 그 모드에 맞는
      행만 골라 로드한다. 로그는 log/70-cspsim-<모드>.log 로 갈라 남는다.

      ── 매번 묻는 값 (시험 조건) ──
        시험 대상       → both (엔터).  ptt / volte / both
        동시 단말 수    → 4 (엔터)
        호 유지 시간    → 10 (엔터)
        시험할 PTT 그룹 → testgrp01 (엔터. data/ptt_groups.csv 의 mcptt_group_id)
                          대상이 volte 면 묻지 않는다
      실행마다 조건을 바꾸는 값이라 저장돼 있어도 매번 묻는다 (현재값이 기본값).

      ── 묻지 않는 값 (사이트 값) ──
        SIP 주소 · PTT/VoLTE 도메인 · DB 값 · OAM 주소 · admin 비번
      화면에 무엇이 쓰이는지는 찍어준다. 바꿔야 하면 --reconfigure 로 실행한다.
      [주의] 도메인을 여기서 바꾸면 안 된다 — 18 단계가 도메인으로 H(A1) 을
             결박했으므로 어긋나면 등록이 401 로 실패한다. 바꿀 거면 18 단계
             (--role db-data --reconfigure)부터 다시 돌려 ha1 을 재발급한다.

      [확인] 통과 조건 — 모드별로 다르다

        구분              PTT 그룹호            VoLTE 호
        ───────────────── ───────────────────── ─────────────────────────────
        등록              Registered : 4 / 4    Registered : 4 / 4
        호 성립           Call OK/End : 1 이상  Call OK/End : 1 이상
        floor(발언권)     GRANT received        해당 없음
        서버측 기록       turn_count > 0        통계 — 참고만 (아래 주의)

      [주의] VoLTE 는 성립 건수가 단말 수의 절반이다 — 단말끼리 짝을 지어 걸기
             때문이다 (단말 4 → 호 2). 그래서 4/4 를 요구하지 않는다.

      [주의] VoLTE 는 즉시 조회되는 호 이력 API 가 없다. 통계뿐인데 그것은
             oam-svc 롤업 주기(StatsRollup.Interval, 기본 60초)를 타므로 호 직후엔
             0 이다. 그래서 통계는 **참고로만** 찍고 판정에 쓰지 않는다 —
             판정에 쓰면 멀쩡한 호가 주기 때문에 실패로 찍힌다.
             값을 보려면 60초쯤 뒤 콘솔 `통계` 화면이나 아래로 확인한다:
               /api/v1/stats/calls?svc=volte&date=<YYYY-MM-DD>

      [주의] PTT 의 "Call OK 인데 turn_count=0" 은 floor 실패다. 등록·호는 되는데
             발언권만 안 되는 상태이며, 원인은 대개 SDP 광고 주소와 실제
             패킷 출발지가 다른 것이다. 스크립트가 -local_ip 를 명시해 이를 막는다.
             판정은 **이번 실행 이후 시작된 세션만** 본다 (옛 이력에 흔들리지 않게).

      [주의] codec(0)=PCMU 는 **그 세션에 미디어 파일이 안 붙었다**는 뜻이다.
             cspsim 은 파일이 있으면 코덱표 최우선(AMR-WB, payload 96)으로 광고하고,
             없으면 합성음 PCMU(0)로 떨어진다. 파일은 이름과 무관하게 순번대로
             돌려 쓰므로(§0-4), 하나라도 있으면 전 세션에 붙는다.
             → codec(0) 이 보이면 media 디렉토리를 못 찾았거나 그 안에
               *_audio.amrwb 가 없는 것이다. 로그의 "미디어 파일 수: audio=N" 을
               본다. 호 성립 판정과는 무관하다 (합성음으로도 호는 선다) —
               녹취 재생만 못 한다.

 7. 문제가 생겼을 때
================================================================================

 공통
   · 실패한 단계만 다시 돌린다:     sudo ./tb-install.sh --role <역할>
   · 여러 단계 중간부터:            sudo ./tb-install.sh --role db --from 15
   · 값을 다시 입력하려면:          sudo ./tb-install.sh --role <역할> --reconfigure
   · 자세한 출력은 로그에 있다:     log/<단계>.log

 증상별
   OS 불일치로 시작부터 멈춤
       Ubuntu 26.04 가 아니다. 진행하면 OAM 이 안 뜬다. 서버 OS 를 맞추는 게 정답.
       그래도 강행하려면 --force-os (권장하지 않음).

   05 단계에서 .deb 설치 실패
       log/05-apt-mariadb.log 를 본다. **맨 앞의 Err: 줄을 먼저** — 색인을 못 읽은
       것과 의존이 부족한 것은 다른 문제다. 그리고 두 표현을 구분해서 읽는다:
         · "not installable"           = 어디에도 없다      → 반입에 추가해야 한다
         · "not going to be installed" = 있는데 연쇄로 막힘 → 위의 진짜 원인을 찾는다
       부족한 것은 빌드 장비에서 다시 수집한다:  tools/tb-fetch-debs.sh <패키지명>

   05 단계 "dpkg 가 깨끗하지 않습니다"
       dpkg 가 반쯤 멈춘 상태에서는 apt 가 **무엇을 해도 거부**한다. 먼저 정리한다:
         sudo dpkg --configure -a
       "in a mess" 로 남은 패키지가 있으면 그것만 다시 설치해야 한다:
         sudo apt-get install --reinstall <패키지>              (인터넷 되는 장비)
         sudo dpkg -i offline/debs/*/<패키지>_*.deb              (폐쇄망)

   05 단계 "Could not open file .../Packages - open (13: Permission denied)"
       apt 는 file:// 저장소를 **_apt 사용자로 권한을 낮춰** 읽는다. 키트가 홈 아래
       (Ubuntu 기본 홈은 0750)에 있으면 _apt 가 통과하지 못한다. 05 단계가 색인·deb 를
       읽을 수 있는 자리로 옮겨 붙이므로 최신 키트에서는 나지 않는다. 옛 키트라면
       반입본을 새로 받는다.

   05 단계 "linux-tools ... libnl-3-200 but it is not installable" (apt 전체가 잠김)
       **MariaDB 와 무관하다.** apt 는 설치 요청 전에 시스템 전체 의존을 검사하므로,
       관계없는 패키지의 구멍이 이 설치까지 거부한다. 그 구멍을 메울 deb 를 반입한다:
         tools/tb-fetch-debs.sh apt-repair      (빌드 장비, 인터넷 필요)
       05 단계는 debs/ 아래 **모든 세트**를 저장소로 붙이므로 apt-repair 를 함께 푼다.

   05 단계가 dpkg 직접 설치로 넘어가지 않는다 (의도된 동작)
       dpkg 는 의존을 해소하지 못해 중간에서 멈추고 시스템을 **반쯤 설치된 상태**로
       남긴다. 그러면 이후 apt 조작이 전부 막혀 상황이 더 나빠진다. 그래서 기본으로는
       시도하지 않는다. 정공법은 apt 가 왜 실패했는지 고치는 것이다.
       그래도 밀어붙이려면:  sudo TB_ALLOW_DPKG_FALLBACK=1 ./tb-install.sh --role db --from 05

   10 단계에서 "root 소켓 접속 실패"
       이미 초기화된 MariaDB 다. root 에 비밀번호가 걸려 있으면 수동으로 관리계정을
       만들고 tb-site.conf 에 TB_DB_ADMIN_USER/PASS 를 넣은 뒤 --role db-schema 로 간다.

   15 단계에서 앱 계정 접속 실패
       앱 계정 허용 host 문제다. 1대 구성이면 % 또는 127.0.0.1 이어야 한다.

   18 단계에서 "login_id 가 users 에 없습니다"
       CSV 사이의 참조가 어긋났다. users.csv 의 login_id 와
       subscriptions.csv 의 login_id 를 맞춘다. (아무것도 반영되지 않은 상태다)

   20 단계 실패
       /opt/cims-agent/modules/oam/current/log/agent_install.log 와
       oam_handover.log 를 본다. 서비스 계정 cims 의 로그인 셸·home 을 먼저 확인.

   20 단계 "systemd --user 사용 불가 (XDG_RUNTIME_DIR=/run/user/<uid>)"
       linger 를 **막 켠 직후**의 경합이다. linger 를 켜면 user@<uid>.service 가 뜨고
       /run/user/<uid> 가 생기는데, 디렉토리가 생긴 뒤에도 매니저가 응답하기까지 시간이
       더 걸린다. 최신 install-agent.sh 는 실제로 응답할 때까지 기다리므로 나지 않는다.
       이미 실패했으면 agent 만 다시 깔면 된다 (enroll 은 건너뛴다):
         sudo ./tools/tb-agent-install-cmd.sh --regen --run
       install-agent.sh 는 enrollment 토큰을 **필수 인자**로 받고 그 토큰은 OAM 이 갖고
       있다 — 손으로 만들 수 없어서 위 도구가 OAM 에서 받아 온다.

   콘솔 모듈 목록에 oam 이 없다
       install.sh 의 self-deploy 는 **agent 가 등록된 뒤에** oam 배포 레코드를 만든다.
       agent 설치가 실패했으면 그 단계가 건너뛰어진다. OAM 프로세스는 돌고 있으므로
       서비스에는 지장이 없지만, 콘솔에서 oam 을 업그레이드·재기동할 수 없고 HA 는
       관리 store 위치의 정본을 잃는다. 채우는 법:
         ① agent 부터 살린다 (위 항목)
         ② 콘솔 → 패키지 설치 → [+ 모듈 추가] → oam (설치 경로 /opt/cims-agent)

   40 단계에서 "패키지가 등록되지 않았습니다"
       §4-3 을 먼저 한다.

   60 단계에서 csp 만 running/up 이 안 됨
       거의 항상 local_nodes primary 누락이다. §4-5 를 다시 돌린다.
       확인:  ss -lntu | grep -E ':(5060|5061|25061)'

   단말이 등록이 안 됨 (CSP 는 정상, 리스너도 열림)
       ① csc 자동프로비저닝 포트가 5060 인지 (기본값 15060 이면 못 붙는다)
       ② 접속서비스 도메인과 단말이 쓰는 도메인이 같은지
       ③ local_nodes 의 bind IP 가 단말이 보는 주소인지

   등록이 401 로 실패
       접속서비스의 domain/auth_realm 과 가입번호 발급 때 쓴 값이 다르다.
       §4-5 의 도메인을 고쳤다면 해당 번호를 다시 저장해 자격을 재발급해야 한다.

   70 단계 "cspsim 을 찾을 수 없습니다"
       cspsim 이 설치되지 않았다. 40 단계의 기본 모듈 목록에 들어 있지만, 옛 키트로
       설치했거나 목록을 줄여 돌렸으면 빠진다. tb-site.conf 의 TB_MODULES 를 고치고
       40 을 다시 돌린다 (이미 깔린 것은 건너뛴다):
         sudo sed -i 's/^TB_MODULES=.*/TB_MODULES="oam-svc cmp csc csp cspsim"/' tb-site.conf
         sudo ./tb-install.sh --role install

   콘솔에 서비스 메뉴(가입자·성능/통계·이력·장애)가 없다
       콘솔이 아직 base 판이다. 서비스 메뉴는 **oam-svc 에 동봉된 번들**로 오고, OAM 은
       정적 디렉토리를 기동 시 1회만 해석한다 — oam-svc 설치만으로는 바뀌지 않는다.
       50 단계가 승격시킨다:
         sudo ./tb-install.sh --role console
       그 뒤 브라우저를 강제 새로고침한다 (Ctrl+Shift+R — 옛 번들이 캐시돼 있다).

   환경변수로 준 값이 무시되는 것 같다
       tb-site.conf 에 저장된 값이 있으면 그것이 쓰인다. 최신 키트는 **환경 > 파일 >
       질의** 순서를 지키고, 환경으로 덮은 키를 시작할 때 알려준다. 옛 키트라면
       tb-site.conf 를 직접 고치거나 --reconfigure 로 다시 입력한다.

   log/ 나 state/ 를 지울 수 없다 (Permission denied)
       sudo 로 돌린 단계가 root 소유 파일을 남긴 것이다. 최신 키트는 로그를 만드는
       자리에서 소유권을 호출자에게 되돌린다. 옛 키트라면:  sudo rm -rf <경로>

   더 자세한 증상별 원인
       docs/user-manual/initial_install.md 의 §8 문제 해결 표가 정본이다.

 설정만 다시:
  $ sudo ./tb-install.sh --role config
  $ sudo ./tb-install.sh --role start

 데이터만 다시 넣기:
  $ sudo ./tb-install.sh --role db-data
      멱등이라 이미 있는 행은 건드리지 않고 바뀐 값만 갱신한다.

 전부 철거(깡통으로 되돌리기):
  $ sudo env -u SUDO_USER bash /opt/cims-agent/uninstall-base.sh --yes
      [주의] env -u SUDO_USER 를 꼭 붙인다. 안 붙이면 호출한 계정의 서비스를
             지우고 정작 cims 계정의 agent 는 살려둔다.

  $ pgrep -af 'cims_agent.py|bin/csp|bin/cmp|oam_app.py|csc_app.py'
      [주의] C++ 모듈(csp/cmp)은 자동 정리되지 않는다. 남아 있으면 직접 종료한다.
             csp 는 SIGTERM 을 잡으므로 kill -9 가 필요할 수 있다.

  $ sudo mariadb -e "DROP DATABASE cims;"
      DB 까지 지울 때만. 지우면 §4-1 부터 다시 해야 한다.

 철거 전에 설정을 받아두면 복구가 짧아진다:
  $ sudo ./tb-install.sh --show > ~/tb-site-backup.txt


================================================================================
 부록 A. 한 번에 다 하기  (익숙해진 뒤)
================================================================================

  $ sudo ./tb-install.sh --role all-in-one
      05→10→15→18→20→30→40→45→50→60 을 순서대로 다 돌린다.
      물어보는 값은 위와 같고, 중간에 실패하면 그 단계부터 이어서 돌리면 된다.

  $ sudo ./tb-install.sh --role callcheck
      호시험은 따로 돌린다.


================================================================================
 부록 B. 이 설치가 손대는 곳
================================================================================

  /opt/cims-agent/                      설치 루트 (모듈·런타임·로그)
  /opt/cims-agent/modules/oam/runtime/  관리 store (설정·컬렉션·서비스 로그)
  /etc/mysql/mariadb.conf.d/99-cims-tb.cnf   MariaDB 접속주소 설정 (배포판 파일은 원본 유지)
  /etc/sudoers.d/cims-priv              agent 권한 위임
  /var/lib/systemd/linger/cims          서비스 계정 상시 세션
  MariaDB 의 cims DB                    가입자·조직·그룹 데이터

  반입한 tarball 과 .deb 은 읽기만 한다 — 풀거나 고치지 않는다.
  모듈 설정도 패키지 안의 json 을 직접 고치지 않고 OAM 설정 경로로만 넣는다.


================================================================================
 부록 C. 사이트 값이 저장되는 곳
================================================================================

  tb-site.conf     이 TB 의 모든 값 (0600). 직접 편집해도 된다.
  state/           임시 자격(DB 관리계정·OAM 토큰). 설치가 끝나면 지워도 된다.
  log/             단계별 로그.

  [주의] tb-site.conf 에는 DB 비밀번호와 콘솔 admin 비밀번호가 들어 있다.
         반출·공유하지 않는다.
